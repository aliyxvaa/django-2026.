# Положение о командном проекте · SFT6206 Django · осень 2026

Кафедра ЦИС МУИТ · преподаватель Сырым Жакыпбеков · группы IT1-2401, IT1-2402, IT1-2403, SIS-2305.
Составлено по образцу Положения хакатона HackAlem AI 2026 (Astana Hub) — те же принципы, масштаб семестра.

## 1. Общие положения
1.1. Курс ведётся как хакатон длиной в семестр: 11 команд по 3–4 человека, у каждой свой репозиторий-продукт на базе каркаса Service Desk (`django-2026`).
1.2. Участие в команде = согласие с настоящим Положением. Правила для ИИ-агентов и Definition of Done — `AGENTS.md` в репозитории команды.
1.3. Официальные каналы: команда **DJANGO** в Teams (объявления), GitHub-организация `iitu-2026-1-sem` (код, задания, оценки).

## 2. Команды и роли
2.1. Состав команд — `README.md` каждого репозитория. Один студент — одна команда.
2.2. **Капитан** (роль `maintainer` в GitHub) — контактное лицо, отвечает за README, распределение задач и рабочий `main`. Капитан = первый вошедший в организацию из состава команды.
2.3. Смена состава — только с согласия преподавателя, до 5-й недели.

## 3. Два репозитория — две линии работы
| | `django-2026` (общий) | `django-tNN-<группа>` (командный) |
|---|---|---|
| Что | Фичи Service Desk по Issue `week-N` | Собственный продукт команды |
| Как | Ветка `feat/<N>-<slug>` → PR → ревью → merge → автодеплой | Свободно внутри команды, `main` всегда рабочий |
| Оценка | Индивидуальная: принятые PR | Командная + вклад каждого по `git log --author` |

## 4. Еженедельный прогресс (аналог п.6.6 Положения HackAlem)
4.1. **Каждую неделю у каждого участника — реальный результат в репозитории:** коммит с кодом, тест, миграция, схема, README-раздел. Пустые коммиты и правки пробелов результатом не считаются.
4.2. Прогресс проверяется автоматически по истории коммитов в понедельник до лекции. Неделя без результата — предупреждение; две подряд — снижение балла команде; три — вопрос о составе.
4.3. Все изменения — только через репозиторий организации. Код, принесённый одним архивом в конце, не оценивается (п.6.8 по аналогии).

## 5. Критерии оценки командного проекта (100 баллов, шкала HackAlem п.7.4)
| Критерий | Что смотрим | Баллы |
|---|---|---|
| Проблема и ценность | Из README ясно: какую проблему решаем, для кого, в чём ценность | 15 |
| Функциональность прототипа | Ключевая механика реализована, основной сценарий запускается | 25 |
| Техническая реализация | Компоненты связаны, структура позволяет развивать идею; не production-quality | 15 |
| Практическая применимость | Понятно, где и кем может использоваться | 15 |
| Потенциал развития | Во что может вырасти | 20 |
| README и воспроизводимость | Понять и запустить без презентации | 10 |

5.1. Первичную проверку делает автоматика: CI (`make check` — ruff + pytest), история коммитов, доступность деплоя. Затем — преподаватель. Аналог AI-судьи п.8.3.
5.2. **Проект должен быть развёрнут** к защите (п.8.7): деплой на сервер курса `tNN.django.alma-ai.cc`. Не запускается — не оценивается.

## 6. Индивидуальная оценка внутри команды
6.1. Базовый балл команды делится с поправкой на вклад: `git log --author`, принятые PR, ревью коллег.
6.2. Участник без коммитов в командном репозитории за семестр получает 0 за командную часть независимо от результата команды.
6.3. На защите любой участник объясняет любую часть кода. Не может — вклад ставится под сомнение.

## 7. Работа с ИИ-инструментами
7.1. Codex, Claude, Copilot и аналоги — разрешены и приветствуются (как на HackAlem).
7.2. Сгенерированный код — понимать и тестировать. Раскрывать в README: «использованы ИИ-инструменты: …» (аналог п.6.4 о раскрытии внешних материалов).

## 8. Основания для незачёта команде (аналог п.12 дисквалификации)
- Подделка истории коммитов (сквош чужих коммитов под своё имя, backdating).
- Чужой код (другой команды, из интернета целиком) без указания источника.
- Один участник пишет всё, остальные не коммитят — незачёт остальным, не команде.
- Секреты (пароли, токены, `.env`) в репозитории.
- Проект не развёрнут к защите.
