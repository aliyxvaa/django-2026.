# Как участвовать (для студентов)

Мы работаем в ОДНОМ репозитории ветками: каждая фича = Issue → своя ветка → Pull Request → ревью преподавателя → merge в `main` → автодеплой.

## 0. Один раз (первая практика)
1. Аккаунт GitHub на корпоративную почту `@iitu.edu.kz`, в профиле — реальное имя (Фамилия Имя) и группа.
2. Примите приглашение в организацию `iitu-2026-1-sem` (письмо на почту или https://github.com/orgs/iitu-2026-1-sem/invitation).
3. Клонируйте репозиторий и запустите проект:
   ```bash
   git clone https://github.com/iitu-2026-1-sem/django-2026.git && cd django-2026
   python -m venv .venv && . .venv/bin/activate        # Windows: .venv\Scriptsctivate
   pip install -r requirements.txt
   python manage.py migrate && python manage.py createsuperuser && python manage.py runserver
   ```
   Откройте http://127.0.0.1:8000 и http://127.0.0.1:8000/admin/.
4. Настройте git: `git config user.name "Фамилия Имя"` и `git config user.email "ваша@iitu.edu.kz"`.

## 1. Цикл одной фичи
1. Возьмите Issue (метки `good first issue`, `week-N`): напишите в нём «беру» и назначьте себя (Assignees). Один Issue — один студент (или пара).
2. Обновите main: `git checkout main && git pull`.
3. Ветка: `git checkout -b feat/<номер>-<кратко>` (пример: `feat/1-ticket-priority`). Имя ветки = ваш номер Issue.
4. Код + тесты + миграции. Проверка: `make check` (ruff + pytest) — должно быть зелёным. Коммиты по делу: `feat(tickets): приоритет заявки (#1)`.
5. `git push -u origin feat/1-ticket-priority` → на GitHub появится кнопка **Compare & pull request** → заполните шаблон, в описании `Closes #1`.
6. Дождитесь CI (зелёная галочка) и ревью преподавателя. Правки — новыми коммитами в ту же ветку (PR обновится сам).
7. После merge ветка удаляется автоматически; `git checkout main && git pull` — и берите следующий Issue.

## 2. Что такое «готово» (Definition of Done)
- Фича работает и покрыта тестами (минимум 1 тест на happy-path + 1 на ошибку/права).
- `make check` зелёный, CI на PR зелёный, конфликтов с `main` нет (`git pull origin main` в свою ветку, если main ушёл вперёд).
- Миграции есть и применяются с нуля.
- Нет секретов, нет закомментированного мусора, нет `print()` — используйте `logging`.
- В PR: что сделано, как проверить, скриншот (если UI).

## 3. Ревью и оценка
Преподаватель ревьюит PR в порядке очереди (обычно в течение 2 рабочих дней). Баллы по силлабусу: работоспособность 4 · качество кода 3 · защита 3.
На защите (практика/СРОП) Вы объясняете свой код и вносите изменение по требованию — сгенерированный ИИ код без понимания = 0 баллов (силлабус §6).

## 4. Правила веток
- В `main` напрямую пушить нельзя (защита ветки) — только через PR.
- Не работайте в чужой ветке без договорённости; не трогайте чужие файлы без нужды.
- Одна ветка = одна фича. Большую фичу разбейте на несколько Issue.
